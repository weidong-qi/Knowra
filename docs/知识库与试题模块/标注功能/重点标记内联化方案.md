# 重点标记内联化方案

> 日期：2026-10-18
> 状态：第 6 节决定已于 2026-10-18 确认；I0、I1、I2 已完成（第 9–11 节）；I3 只读试运行已完成（第 12 节），正式迁移待用户核对报告。
> 取代：[重点标记稳定身份迁移方案](重点标记稳定身份迁移方案.md) 的 S3、S4 不再实施；S1 的编辑器 mark 和块 ID 可复用。
> 目标：重点的位置由正文自身携带，服务端不再推断位置；同一套行内标记为后续"挖空"复习功能预留。

## 1. 为什么改

现有做法让 Markdown 保持干净，重点存在正文之外，因此每次保存都要推断"这段区间还是不是原来那段"。代价（2026-10-18 统计 Mac 应用本地库）：

| 项 | 数量 | 体积 |
| --- | --- | --- |
| 重点 `contentAnnotations` | 124 条（活跃 80 条，分布在 9 篇笔记） | 368KB |
| 修订 `annotationRevisions` | 722 条 | 1.8MB |
| 笔记正文 `notes` | 38 篇 | 1.0MB |

- 一条重点把位置存了 5 遍（旧坐标、`anchor`、`originSnapshot`、`identityBinding`、各类 hash），摘录文字存了 3 遍。
- `reconcileForNote` 在正文一变时，对笔记里每条活跃重点都升修订号、写一条含新旧完整锚点的修订记录，位置没变也一样。
- 每条重点、每一步编辑都会整篇调用一次 `projectMarkdown`，没有缓存。
- 跟随规则复杂，"待确认"状态主要就是推断不准的产物。

用户已确认：可以接受导出的 Markdown 带标记（挖空功能本来也要在正文里留标记）。

## 2. 标记语法

原则：用 HTML，在其他 Markdown 查看器里也能退化成可读的样子；短属性名；类型和重要度跟着正文走，长文本留在元数据表。

### 2.1 行内（选区重点、挖空）

```markdown
勾股定理指出 <mark data-k="a1b2" data-t="key" data-l="core">直角三角形两直角边平方和等于斜边平方</mark>。
```

| 属性 | 含义 | 取值 |
| --- | --- | --- |
| `data-k` | 标记 ID，笔记内唯一，字母数字和 `_-`，编辑器生成 8 位 | 编辑器生成 |
| `data-t` | 角色，空格分隔，可多值 | `key`（重点）、`cloze`（挖空），如 `"key cloze"` |
| `data-c` | 重点类型，省略即 `important` | `question` / `supplement` / `pitfall` / `temporary` |
| `data-l` | 重要程度，省略即 `normal` | `important` / `core` |

- 一个 `<mark>` 只带一个 ID，并且必须在同一行内闭合：跨行（包括软换行、硬换行）的选区按行切段，共用同一个 ID。这样按行的 diff、合并也不会拆坏标记。
- 跨块的选区同样拆成每块一个 `<mark>`，共用同一个 `data-k`。
- 两个重点部分重叠时按边界切段并嵌套（`<mark a>…<mark b>…</mark></mark><mark b>…</mark>`），保证 HTML 合法、不交叉。
- 行内代码、行内公式是整体：标记只能整个包住，不能只标其中一部分。
- 不带 `data-k` 的 `<mark>`、用户自己的 `==高亮==` 都是普通样式，与重点无关。

### 2.2 块级（整块、整节、列表）

块级标记用 HTML 注释，在其他查看器里不可见。注释内是 `k`、标记 ID，再加若干 `键=值`；键与行内属性同名（去掉 `data-`），值做 URL 编码：

~~~markdown
## 牛顿第二定律 <!--k c3d4 s=section l=core-->

- 动量守恒 <!--k e5f6 s=list-->

一段被整块标记的正文。 <!--k g7h8 s=blocks-->

<!--k g7h8 s=blocks-->
```python
print("代码块也可以是成员")
```
~~~

| 键 | 含义 |
| --- | --- |
| `s` | 范围：`section` / `list` / `blocks` / `code` |
| `t`、`c`、`l` | 同行内的角色、类型、重要程度 |
| `r`、`h` | 仅 `s=code`：代码内容中的字符区间 `起-止`，和所覆盖文字的校验值 |

位置规则：

- 标题、段落、列表项：放在块**首行末尾**，前面一个空格。整行移动、复制时自然跟着走。如果行尾有结尾空白、硬换行反斜杠或 ATX 标题的闭合 `#`，标记写在它们**之前**，不改变原有语义。
- 代码块、公式块、表格、HTML 块：放在块**前一行**，单独成行。这些块的首行是字面内容或结构语法，不能追加注释。
- 同一位置有多个标记时连写在一起，如 `<!--k a1 s=blocks--><!--k b2 s=code r=0-12 h=1x9k-->`。

| 范围 | 落在哪里 | 范围怎么算 |
| --- | --- | --- |
| `section` | 标题行 | 读取时现算到下一个同级或更高级标题（规则不变） |
| `list` | 列表项首行 | 该项的完整子树（规则不变） |
| `blocks` | 范围内**每个**块都带同一 ID | 带该 ID 的连续块，成员关系显式写在正文里 |
| `code` | 代码块前一行 | 代码内容的 `r` 区间；`h` 不符（代码块在编辑器外被改过）时视为未落位，不猜位置 |
| 标题局部排除 | 被排除的块带 `<!--k- {id}-->` | 现算的章节范围减去这些块 |

代码块内的范围不能用 `<mark>`，因为代码块里的 HTML 是字面文字。真实数据里 27 条选区重点有 17 条涉及代码块（"问题段落 + 代码答案"），其中 2 条只选了代码的一部分，所以 `s=code` 是必需的。一个选区跨过段落和代码块时，段落部分用 `<mark>`，代码部分用 `s=code`，共用同一个 ID。

### 2.3 编辑器

- 行内：复用 S1 的 `knowraAnnotation` mark，去掉 `annotationSerializerGuard` 的剥离，改为序列化成 `<mark>`；解析时读回。
- 块级：作为块节点属性（`annotation`），序列化时追加注释；拖动、剪切粘贴时随节点一起移动。
- 复制粘贴：粘贴范围内出现重复 ID 时换新 ID（沿用 `editorBlockIdentity` 的"插入范围内换新"规则），副本成为新重点。
- 撤销/重做：标记就是文档内容，由 ProseMirror 历史天然处理，不再需要 `snapshots`、`cut`、`moving` 等旁路。

## 3. 数据模型

### 3.1 正文是位置的唯一来源

`contentAnnotations` 只保留元数据，不存位置：

| 保留 | 说明 |
| --- | --- |
| `id`、`spaceId`、`noteId` | `id` 由"笔记 ID + 标记 ID"确定性生成（`annotation-k-…`），`idempotencyKey` 为 `knowra-mark:<标记 ID>`；多台设备各自派生得到同一行 |
| `comment`、`sourceMode` | 备注长文本不进正文 |
| `lifecycleStatus`、`createdAt`、`updatedAt`、`deletedAt` | 取消/恢复 |
| `quoteText`、`headingPath`、`scopeType`、`kind`、`importance` | **派生缓存**：每次保存时从正文重建，供列表、筛选、跨笔记查询和 AI 读取，不作为位置依据。位置不缓存（I2 起固定写 0/1），否则上方打字会让整篇的重点行每次都被重写 |

I2 以 `schemaVersion: 3` 与旧行共存，暂不改表结构：NOT NULL 的旧字段写派生值或常量，`anchor` 只记 `{ format: 'knowra-inline', markId, scopeType, roles }`，`originSnapshot` 保留以满足同步校验。I4 删除旧链路时再删除：`fromPosition/toPosition`、`prefixText/suffixText`、旧格式 `anchor`、`identityBinding`、`anchorFingerprint`、`noteContentHash`、`resolvedContentHash`、`boundaryFingerprint`、`anchorStatus`、`anchorReason`、旧 `status`、`schemaVersion` 1。

### 3.2 保存时的派生

保存笔记时解析一次正文，得到全部标记：

- 正文有、表里没有 → 新建元数据行（编辑器通常已先建）。
- 表里活跃、正文没有 → 标为 `deleted`，保留最后的 `quoteText` 和所在块的上下文，供恢复。
- 两边都有 → 刷新派生缓存；**只有元数据真的变了才升修订号**。

整篇只解析一次，开销和笔记长度成正比，与重点数量无关。

### 3.3 修订记录

`annotationRevisions` 只记用户可见的变更（创建、改类型/备注/重要度、取消、恢复），不再记 `sourceReconciled`。快照里只存派生摘要，不存锚点。现有 722 条中的 `sourceReconciled` 可在迁移后清理（`AnalysisScopeSnapshot` 引用到的除外）。

### 3.4 必须同步修改的判断：正文"是否改动"

加/去标记会改变 `rawMarkdown`。以下判断改为比较**去掉标记后的文本**，否则打一个重点就会让依赖它的东西全部失效：

- 知识证据健康：`knowledge-item-service.ts:115` 比较 `version.content !== note.rawMarkdown`。本地库现有 33 条证据全部是 `noteVersion` 来源，不改的话迁移当天全部变 `stale`。
- MCP 读取：`mcp-knowledge-read.js:77`、`:207`、`mcp-read-snapshot.js:112` 是"当前正文对应的版本记录是否一致"的完整性校验，标记本身是正文的一部分，**不改**（I2 复核后确认）。
- 笔记版本：只改标记的保存仍生成新版本（历史可回看重点变化）。按"去标记后的正文 hash"合并相邻同文版本留到 I3，届时按真实打重点频率决定。
- 搜索、字数统计的纯文本与大纲：去掉标记（I2 已做）。AI 读取的正文暂时保留标记，AI 能看到哪些是重点；是否另附结构化清单留到 I3。

提供共享函数 `parseKnowraMarks(markdown)`、`stripKnowraMarks(markdown)`，放在 `@study-accelerator/shared/knowra-marks`（不放 `content-anchor`：该包有公共导出冻结，且 I4 后大部分会删除）。

## 4. 编辑器以外的改写

AI、MCP 写入、同步合并都是直接改正文文本：

- 同步合并：标记就是文本，冲突合并自然带上，不再有"正文合并了但锚点没合并"的问题。
- AI/MCP 改写：写入工具说明里要求保留 `<mark data-k>` 和 `<!--k ...-->`；服务端保存后对比前后 ID 集合，丢失的重点在变更回执里列出，并在笔记里提示"本次外部改写移除了 N 个重点，可撤销"。不做按文字猜测复原。
- 用户在源码模式手改标记：按改后的正文为准；语法不合法的标记保留原文，不当作重点，并在检查器里提示。

## 5. 旧数据迁移

一次性迁移，按笔记执行，先整库备份（沿用现有升级备份目录 `Knowra-upgrade-backups`）。

1. **试运行**：只输出报告，不写入。按笔记列出可落位/不能落位的重点、生成的新正文 diff 预览。
2. 活跃且 `resolved` 的 v2 重点：按 `anchor.sourceStart/sourceEnd`（源码偏移）插入标记；`section`/`list` 写到根块首行，`blocks` 写到每个成员块，排除项写 `<!--k- -->`。同一笔记内的插入从后往前做，避免偏移错位；插入后用 `stripKnowraMarks` 校验正文与原文完全一致。
3. `needsReview`/`missing`/v1 旧重点（本地现有活跃 2 条加 1 条旧数据）：不猜位置，保留元数据并标为"未落位"，在检查器里列出，用户可以重新选择或放弃。
4. 已取消（`deleted`）的重点：只保留元数据，不写入正文。
5. 每篇笔记迁移生成一个新版本，标注来源为"重点迁移"；知识证据按 3.4 的新规则不受影响。
6. 迁移成功后，笔记的 `annotationStructure` 里的身份表停止维护。

## 6a. 扩展规则

后续功能复用同一套标记时遵守：

1. **只有必须随文字移动的信息才进正文。** 进正文的只有 ID、角色和少量短属性；备注、复习记录、关联关系等放在以标记 ID 为键的独立表里。
2. **新功能 = 新角色或新属性。** 行内在 `data-t` 里加角色值，块级在注释里加范围或角色；不另起一套语法。
3. **未知的角色和属性原样保留。** `parseKnowraMarks` 和编辑器遇到不认识的 `data-*` 属性或角色时，不丢弃、不报错，序列化时原样写回，这样旧版本应用打开新数据不会造成损坏。
4. **`stripKnowraMarks` 对所有角色一视同仁**，新功能不需要改导出去除逻辑。
5. 属性名统一用 `data-` 加一个字母，新增前在本节登记，避免冲突。

| 属性 | 用途 |
| --- | --- |
| `data-k` | 标记 ID |
| `s` | 块级范围（仅注释形式） |
| `r`、`h` | 代码区间与校验（仅 `s=code`） |
| `data-t` | 角色：`key`、`cloze` |
| `data-c` | 重点类型 |
| `data-l` | 重要程度 |
| `data-g` | 挖空分组（预留） |
| `data-h` | 挖空提示（预留） |

## 7. 挖空（后续功能，本方案只预留）

- 挖空就是 `data-t` 含 `cloze` 的行内标记；把重点变成挖空只是加一个角色，`<mark data-k="a1b2" data-t="key cloze">`。
- 可选属性：`data-g`（分组，同组一起显示/隐藏，对应 Anki 的 `c1`、`c2`）、`data-h`（提示文字）。
- 复习视图只读渲染：挖空处显示占位，点击揭示；复习记录（对错、间隔）存在独立的表里，按 `annotationId` 关联，不写进正文。
- 导出到 Anki 时转成 `{{c1::答案::提示}}`，属于导出转换，不改变存储语法。

## 9. I0 实施记录（2026-10-18）

### 9.1 已实现

- `packages/shared/src/knowra-marks.js`（`@study-accelerator/shared/knowra-marks`）：`parseKnowraMarks`、`stripKnowraMarks`、`insertKnowraMarks`、`formatKnowraMarkOpen`、`formatKnowraMarker`、`knowraCheck`。没有放进 `content-anchor`，原因见 3.4。
- 文本层扫描，不依赖 Markdown 解析器：跳过围栏代码、`$$` 公式块、行内代码、转义、实体和普通注释（含跨行注释）。不带 `data-k` 的 `<mark>` 及其他 HTML 元素参与嵌套配对，但不算标记。
- 不合法的标记（ID 非法、未闭合、属性无法解码、代码区间越界或校验不符）计入 `problems`，去除时当作普通文字保留。
- 用户自己写的 `<!--k 备注-->`（没有 `键=值`）不算标记，也不报问题。

### 9.2 验证

- `packages/shared/test/knowra-marks.test.js`：12 项，包括 300 轮随机文档往返测试（插入后去除逐字还原，解析能找回全部 ID）。
- Mac 本地库只读核对（不提交数据）：38 篇笔记、约 59 万字符，误识别 0。
- 迁移预演：80 条活跃且已定位的重点全部能插入；去除后逐字还原，解析无问题；整库耗时约 36ms。

### 9.3 预演发现、留给 I3 的规则

1. "整块"重点有 7 条起点落在代码块内容里，标记的其实是代码块本身，迁移时挂到开围栏行（`lineBefore`）。
2. 选区在源码里会被 Markdown 语法切成几段（如 `\*` 转义两侧），同一行的几段先合并成一段再插入。
3. 文本层校验挡不住"与强调、链接交叉"（如 `**粗**体` 只选 `粗体`）。I3 需要按 mdast 把范围扩展或切分到兄弟节点边界，再调用 `insertKnowraMarks`。
4. 引用块（`>`）里的代码块不按代码块识别，I1 编辑器里先不允许在其中标代码范围。

## 10. I1 实施记录（2026-10-18）
