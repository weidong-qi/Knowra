# V1 旧重点维护步骤

本步骤承接方案第 14.6–14.7 节，仅处理那条父笔记在回收站、原范围不匹配、缺失结构锚点和原始快照的活跃 v1 重点。选定行为是云端标准取消，保留原文、笔记版本和私有历史。禁止直接改数据库、补造快照、恢复笔记或自动转为 v3。

## 1. 开发与真实维护的边界

代码与合成回归在独立分支和工作目录内进行，用户可正常使用 App。真实维护前，先让已有客户端完成正常同步，核对没有未确认请求或冲突，再保存并退出 App，暂停其他设备编辑。退出 App 不会自动清空待同步队列，不能跳过同步便进入维护。

本批工具只生成两个资料快照及预检计划，没有执行取消、清理队列、回收或部署的能力。`ready-for-maintenance-window` 只表示所选两个快照一致，不代表活动资料仍一致，也不是执行授权。真实操作时必须重新核对部署版本、当前活动路径、revision、引用、队列和其他客户端状态。

## 2. 取得快照与预检

1. 核对云端活动 release、真实数据目录与源文件 hash。从活动路径取得完整 JSON 副本，存放在仓库外的私有目录；取回后与远端 hash 比对。不要将旧导出当成活动云端状态。
2. 指定 Mac 资料根目录；工具通过 `active-dataset.json` 选择恢复后的活动资料。不要猜测固定的 `offline/local.sqlite` 总是活动库。
3. 指定一个尚不存在的输出目录（父目录应当私有），执行：

```bash
node scripts/prepare-v1-annotation-maintenance.mjs \
  --cloud-source="<刚核对过的云端 JSON 副本>" \
  --local-root="<Mac 资料根目录>" \
  --output-dir="<新的私有维护目录>"
```

输出目录权限为 `0700`，文件为 `0600`：

| 文件 | 内容 |
| --- | --- |
| `cloud.json` | 输入云端副本的完整原始字节，含私有扩展 |
| `local.sqlite` | SQLite 在线备份 API 产生的一致性数据库快照，含 WAL 中已提交的实体、私有表和同步队列 |
| `plan.json` | 来源路径、两份备份的 SHA-256、基线指纹、报告；仅快照就绪时包含带 `expectedRevision` 的标准 DELETE 请求描述 |
| `report.json` | 可分享的计数、诊断和阻塞原因，不含对象 ID、正文、标题、来源路径或请求 |

这是数据库维护快照，不包含附件文件和完整 App 安装资料；不能替代全量灾备。读取或版本验证失败时，已取得的快照仍保留，不会生成成功计划。来源发生变化时重新取快照，禁止复用旧计划继续执行。

退出码 **0** 为两个快照就绪；**2** 为计划受阻；**1** 为参数、读取、格式或版本错误。阻塞时 `plan.json.request` 必须为 `null`。待同步统计按核对器的条目口径计算，不是待同步笔记数。

预检复用活动资料检查器与私有历史所属模块的只读校验器，必须满足：

- 两端都恰有一条活跃 v1；原始重点、父笔记、绑定版本及关联修订一致。对象键和修订存储顺序不影响比对。
- 父笔记仍在回收站，绑定版本 hash 正确，摘录在当前与历史投影中各出现一次；旧范围在两种文本中仍不匹配，无结构锚点、原始快照、备注或排除区间。变化时重新决定方案。
- 私有记录和同步覆盖完整，本机没有任何未确认队列；目标本身及关联修订/排除没有核心业务保护引用。
- 在内存副本运行标准取消，并复用云端 JSON 的历史保留策略、受影响笔记范围和私有保留根预演提交；包括新取消修订，以及原当前修订失去自保后的裁剪。`retentionPreview` 仅报告四个历史集合的预计删除数量，任一非零即以 `history-retention-side-effects` 阻塞，不生成请求。过期、采样、数量及字节上限均按现行策略计算，不只核对目标绑定版本。
- 私有历史可以继续包含旧引用和副本；它们必须保全，不能为了通过预检而删除。快照就绪也不代表已满足整个 I4c 删字段条件。

标准 DELETE 会在同一事务提交时运行保留策略，因此 HTTP 200 不代表旧历史全部保留。遇到历史裁剪阻塞时停止维护，另行设计历史保全方案；不能先删除旧历史来消除阻塞，也不能绕过正常事务执行请求。此处只预演实际发送请求的云端 JSON 提交；客户端采用同步下行路径，不模拟本地业务取消。时间推进可能使保留期限到期，维护窗口必须以新快照重新预检。

## 3. 在维护窗口执行标准取消

此步骤尚未自动化，须在用户安排的停用窗口单独执行。

1. 复核实际运行代码支持同一标准取消行为；主线合并和 CI 不等于云端已部署。若部署较旧，先只读审查相关路由/服务并在隔离副本演练，或按正常发布流程升级后重新预检。
2. 重新确认所有待维护端已同步并停用、活动 JSON 与 Mac 快照对应。重新取快照并预检历史裁剪，复核当前 v1 revision、父笔记及绑定版本指纹、核心引用与队列；变化或阻塞就停止。云端也保留可校验的就地备份，不能只依赖 Mac 上的副本。
3. 从私有计划读取目标，向实际服务发送标准 `DELETE /api/knowledge/annotations/:id`，JSON 请求体携带 `expectedRevision`。经过现有服务/事务/同步日志写入，不直接编辑 JSON 或 SQLite。
4. 遇到 409 必须重新核对；网络结果不确定时先查云端当前状态和修订，禁止盲目重试。保留原始请求和结果记录，日志不得发布正文或对象 ID。

## 4. 下行与保全验收

- 云端目标变为 `deleted`，revision 增加一次，有明确的 `deletedAt` 和取消修订。
- 父笔记仍在回收站；原始正文、所有原有版本、摘录、旧偏移、空锚点/原始快照保持原值。旧私有历史及其原始 JSON/hash 保留。
- 已有客户端正常下行，再用隔离的新客户端同步；两者取消状态与云端一致，没有未确认请求、冲突或意外上传。
- 备份并重开取消后的 SQLite，仍保持取消状态和历史内容。此处的新客户端是验收用临时目录，不能替换真实 Mac 活动指针。
- 最后重新执行活动资料检查，保存脱敏报告；逐项记录已安装客户端、其他离线设备和旧备份的兼容状态。未验证的端明确标记，不能以单机合成测试替代。

## 5. 留存与后续批次

v1 的七天留存从实际 `deletedAt` 开始，不从开发、建分支或旧 v2 的取消时间开始。原 111 条 v2 最晚留存期限为北京时间 **2026-11-08 21:51:04**。日期到期不等于实际回收；私有引用和其他保护规则仍可能保留旧行。

完成取消、下行验收和真实回收核对后，才评估删除旧字段、`Note.annotationStructure`、兼容分支和共享包旧导出。当前仍保持业务 schema8、同步格式9、SQLite 物理版本7。
