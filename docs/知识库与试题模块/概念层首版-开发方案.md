# 概念层首版：开发方案

日期：2026-11-12。状态：开发中；2026-11-12 用户确定直接合并、不提供撤销合并；解除关联影响关系时，经一个弹窗确认后一并删除。  
依据：[知识模型独立意见与推进顺序](讨论记录/2026-11-11_知识模型独立意见与推进顺序_Claude.md)（用户已同意）、[领域冻结稿](基础/Knowra%20知识与考卷系统领域冻结稿.md)。  
实现参照：[个人待办首版-技术方案](../打卡与待办/个人待办首版-技术方案.md)（PR #357）。概念层新增的是同一类东西——一组需要跨端同步的新集合——因此沿用它已验证的接入方式，不另起一套。

本文只定技术做法。代码由后续开发任务完成。

## 1. 范围

**第一期做（概念与挂靠）**

- 概念：新建、改名、区分标签、别名、关注 / 不关注、归档、删除与撤销。
- 挂靠：把已有知识点挂到概念上，角色分“主体”和“提及”；改角色、移出、整批移到另一个概念。
- 直接合并：迁移关联与关系、去重，将源名称收为别名；不提供撤销合并。
- 概念列表、概念页；知识点详情显示所属概念。
- 三类新集合的存储、校验、同步和备份恢复（包括第二期才用到的“概念关系”，见第 2 节的说明）。

**第二期做（关系与图）**：手工建立概念关系、由条目投影关系、概念图改用真实数据。

**第三期做（AI 挂靠）**：只列接口约束，见第 8 节。

**不做**：掌握度与颜色聚合（等试题库产生作答证据）、AI 自动合并、检索索引、`KnowledgeItem` 与 `LearningObjective` 的任何字段变更、旧知识点的自动迁移。

## 2. 总体结构

| 层 | 位置 | 说明 |
| --- | --- | --- |
| 共享类型与纯逻辑 | `packages/web-core/src/knowledge-concepts/` | 记录类型、校验、命令规则、视图函数；API、桌面端、前端共用。保持框架、CSS、DOM 无关 |
| API 服务与路由 | `apps/api/src/modules/knowledge-concepts/`（`service.ts`、`routes.ts`、`postgres-store.ts`） | 独立小模块，不放进 `modules/knowledge` 的同步 / 异步双实现里。在 `app.factory.ts`、`postgres-app.factory.ts` 装配，`server.ts` 注册路由 |
| 存储 | JSON 核心集合、SQLite 核心表、PostgreSQL 新表与迁移 | 三种驱动都实现；PostgreSQL 失败不回退 JSON |
| 同步 | `modules/sync/` 新增 `concept-batch-domain.ts`；`desktop-runtime` 的 `entity-batches` / `entity-sync-state` 识别新集合 | 新必需能力 `knowledge-concepts-v1` |
| 前端 | `apps/web/src/features/knowledge/concepts/` | hash 路由 `#/knowledge/concepts`；只用 `components/ui/` 组件 |

**为什么第一期就把“概念关系”的存储和同步做掉：** 新集合要作为必需同步能力加入，云端与 Mac 应用必须一起升级。关系集合如果留到第二期再加，就要再升级一次能力、再协调一次两端升级。所以三类集合在第一期一次接入，第二期只加界面和命令入口的使用。

**为什么同步不延后：** Mac 应用写的是本机 SQLite。SQLite 不认识新集合，Mac 上就完全用不了概念，而不只是“暂时不同步”。待办的做法已经证明这条路径可行。

## 3. 数据模型

三个集合，记录都带 `id`、`revision`（从 1 递增）、`createdAt`、`updatedAt`、`deletedAt`（软删除）。

### 3.1 `knowledgeConcepts`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` | string，1–80 字 | 规范名称 |
| `sense` | string，0–80 字 | 区分标签，只写“它是什么、属于哪个语境”，不写性质、条件、方法 |
| `aliases` | string[]，最多 20 个 | 别名；不含 `name` 本身，互不重复 |
| `reviewStatus` | `candidate` / `confirmed` / `archived` | 手工新建直接为 `confirmed`；`candidate` 留给第三期 |
| `sourceMode` | `manual` / `ai` | 第一期只接受 `manual` |
| `focus` | `active` / `muted` | 个人状态：关注 / 不关注。只影响展示，不影响身份 |
| `mergedInto` | string \| null | 仅为已删除源概念记录合并去向，不参与有效数据的读取或映射 |

规则：

- **同名必须能区分。** 名称归一化（NFKC、去首尾空白、合并连续空白、不区分大小写）后，未删除且未合并的概念里，`name + sense` 不得重复。新名称与已有名称或别名相同时，命令返回 `CONCEPT_NAME_AMBIGUOUS`，要求填写不同的 `sense`；不自动合并。
- **直接合并。** 合并目标必须有效。事务内迁移全部有效关联与关系；重复挂靠按主体优先去重，重复边去重、自环软删除。源概念软删除且禁止恢复，源名称和别名并入目标别名（仍遵守数量与消歧规则）。目标可以继续合并；有效数据不保留合并链。

### 3.2 `knowledgeConceptLinks`（条目-概念关联）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `knowledgeItemId` | string | 必须是存在且未进回收站的 `KnowledgeItem` |
| `conceptId` | string | 必须是未删除、未合并的概念 |
| `role` | `subject` / `mentions` | 主体：这条知识讲的是它。提及：这条知识用到了它 |
| `reviewStatus` | `candidate` / `confirmed` | 手工挂靠为 `confirmed` |
| `sourceMode` | `manual` / `ai` | 第一期只接受 `manual` |

规则：

- 未删除的关联里，`knowledgeItemId + conceptId` 唯一。
- 一条知识点可以有多个主体概念（例如一条比较类条目）；不设上限，不要求至少一个。
- 关联只存身份和角色，不存任何正文。

### 3.3 `knowledgeConceptRelations`（概念关系）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `fromConceptId` / `toConceptId` | string | 两个不同的、未删除且未合并的概念 |
| `type` | 见下 | 关系类型 |
| `basisItemId` | string \| null | 承载这条关系说明的知识点 |
| `reviewStatus` | `candidate` / `confirmed` | — |
| `sourceMode` | `manual` / `ai` | — |

规则：

- 关系类型：冻结稿第 3.8 节的六类（`partOf`、`prerequisiteOf`、`contrastsWith`、`causes`、`appliesTo`、`relatedTo`）加 `isA`。
- **关系记录不存说明文字。** 需要解释时，说明写在一条 `KnowledgeItem` 里，由 `basisItemId` 指向它。
- `basisItemId` 非空时，该知识点必须同时与关系两端的概念有未删除的关联。
- `basisItemId` 为空只允许 `sourceMode = manual`（用户手画的骨架）。
- 同一对概念、同一类型、同一方向只能有一条未删除的关系；`contrastsWith`、`relatedTo` 不分方向。

### 3.4 与知识点生命周期的关系

- **知识点进回收站：** 关联和关系保留；视图函数过滤掉已进回收站的知识点。恢复后自动重新出现。
- **知识点永久删除：** 同一事务内把它的关联、以及以它为 `basisItemId` 的关系软删除；清理预检（`knowledge-item-purge.ts` 的预览）列出受影响的数量。这样不需要给新集合开硬删除通道。校验只检查未删除的记录，已软删除的记录允许指向不存在的知识点。
- **概念删除：** 软删除概念，同一命令软删除它的关联和关系；撤销时一并恢复（按同一 `operationId` 写入的记录）。

### 3.5 存储形态

- **JSON：** `LOCAL_DATA_COLLECTIONS` 加三个集合，`LOCAL_DATA_SCHEMA_VERSION` 由 8 升到 9，旧文件缺少这三个集合时按空数组读入。记录校验放在 `local-data-schema.ts`，跨集合引用校验放在 `local-data-relations.ts`（概念存在、知识点存在、合并目标合法、唯一性）。
- **PostgreSQL：** 三张新表，结构与 `PersonalTodo` 相同（`id`、`data` JSONB、`updatedAt`），字段与引用规则由应用层用 web-core 校验。迁移目录名接在 `m_personal_todos` 之后，用 `n_knowledge_concepts`。写入事务内除三张表外，还要读取 `KnowledgeItem` 的 `id` 和 `deletedAt` 用于引用校验。
- **SQLite：** 按待办在桌面端的做法加核心表。

选 JSONB 而不是带外键的关系表，理由是：记录整条同步、规则已经集中在 web-core、个人数据量下全量读取足够。代价是数据库本身不保证引用完整，靠事务内校验保证。

## 4. 命令（服务端唯一写入口）

`POST /api/knowledge/concepts/commands`，请求体 `{ command }`，命令带 `operationId`（幂等）和目标记录的 `expectedRevision`。一次命令在一个事务内完成，返回本次变更的全部记录。

`GET /api/knowledge/concepts` 返回 `{ concepts, links, relations }`（全部未删除记录），前端在内存里组装视图。知识点正文仍通过现有 `/api/knowledge/items` 读取。

| 命令 | 作用 | 期次 |
| --- | --- | --- |
| `createConcept` | 新建概念；可带 `itemIds` 和 `role`，一次完成“由知识点创建概念” | 一 |
| `updateConcept` | 改名称、区分标签、别名、关注状态 | 一 |
| `archiveConcept` / `restoreConcept` | 归档与恢复 | 一 |
| `deleteConcept` / `undeleteConcept` | 软删除与撤销，连同关联和关系 | 一 |
| `mergeConcept` | 迁移关联和关系、去重、保留别名并停用源概念；不可撤销 | 一 |
| `linkItems` | 把一批知识点挂到一个概念，指定角色 | 一 |
| `setLinkRole` | 改角色 | 一 |
| `unlinkItems` | 移出 | 一 |
| `moveLinks` | 把一批知识点从概念 A 移到概念 B（降级、拆分都用它） | 一 |
| `createRelation` / `updateRelation` / `deleteRelation` | 概念关系 | 二（规则和校验第一期就实现并测试） |
| `confirm…` 系列 | 候选转确认 | 三 |

错误码（HTTP 状态）：`CONCEPT_NOT_FOUND`（404）、`CONCEPT_REVISION_CONFLICT`（409）、`CONCEPT_NAME_AMBIGUOUS`（409）、`CONCEPT_MERGED`（409）、`CONCEPT_INVALID_INPUT`（422）、`CONCEPT_LINK_EXISTS`（409）、`CONCEPT_ITEM_NOT_FOUND`（404）、`CONCEPT_RELATION_BASIS_INVALID`（422）、`CONCEPT_RELATION_EXISTS`（409）、`CONCEPT_AI_SOURCE_RESERVED`（422）、`KNOWLEDGE_CONCEPTS_UNAVAILABLE`（503，存储不支持时）。

**合并后的读取：** 全部有效关联直接指向目标，读取不追踪旧身份。合并弹窗明确提示不可撤销，并说明重复关联、重复边与内部边的处理。

**一键连带删除：** 解除或移动关联导致关系依据失效时，弹窗展示将删除的关系，点击一次确认即可在同一事务完成。命令携带确认的关系 ID 清单；服务端重新计算，范围变化则拒绝并要求重新确认，避免漏删或误删。

**操作元数据：** 三类记录保存最后的 `operationId` 和软删除来源 `deletedBy`。概念保存 `{ id, hash }` 命令回执，随数据同步和备份；同 ID 不同请求拒绝，重复请求返回当前状态。每次关联变更也递增所属概念的版本，作为聚合并发检查。

## 5. 同步

- 新能力 `knowledge-concepts-v1`，集合为上述三个，加入 `WRITABLE_COLLECTIONS` 和必需能力；实体 schema 版本是否需要变动，按待办接入时的结论处理（当时保持不变，由必需能力拦截旧端）。
- **一次命令 = 一个变更批次**，云端整批接受或整批拒绝。
- **云端再校验一遍规则**（`concept-batch-domain.ts`，调用 web-core 的同一套校验）：引用存在、唯一性、有效关联不指向已合并源概念、关系依据合法。
- **引用闭包：** `entity-contract.ts` 的 `SyncReferenceEntity` 补 `conceptId`、`fromConceptId`、`toConceptId`、`basisItemId`、`mergedInto`；关联与它引用的概念、知识点同批或先于它到达。
- **只做软删除：** 同步不接受这三个集合的硬删除。
- **冲突：** 沿用现有实体冲突流程（采用云端 / 采用本机），不做字段级合并；`syncConflictModel.ts` 补三个集合的中文名称和摘要。
- **升级顺序：** 云端与 Mac 应用一起升级；旧版 Mac 被提示升级，本地数据保留。

需要改动的位置以待办接入时动过的文件为清单（`git show --stat` PR #357 可得），目前已确认包括：

- API：`local-data-types.ts`、`local-data-schema.ts`、`local-data-relations.ts`、`attachment-deletion-preflight.ts`、`postgres-snapshot-service.ts`、`migration/` 下的 `json-to-postgres.ts`、`migration-records.ts`、`migration-client.ts`、`db-mappers.ts`，`modules/knowledge/infrastructure/postgres/mappers.ts`，`modules/sync/` 下的 `entity-contract.ts`、`batch-domain.ts`、`domain-types.ts`、`postgres-batch.ts`、`postgres-provider.ts`、`postgres-types.ts`、`postgres-state-types.ts`。
- 桌面端：`entity-batches.mjs`、`entity-sync-state.mjs`、`private-history-validation.mjs`、SQLite 存储，以及仿 `personal-todo-sync.mjs` 的概念同步辅助。
- 知识点永久删除的三条实现路径都要接上第 3.4 节的规则：本地 `knowledge-item-service.ts`、PostgreSQL 的 `postgres-async/knowledge-domain-service.ts`、桌面端 `authoritative-purge.mjs`。**这一处我只确认了文件存在，没有逐行读过清理流程，实现前需先核对。**

## 6. 前端（第一期）

入口：知识工作区顶部加成组切换（`SegmentedControl`）：知识点 / 概念 / 概念图。`KnowledgeStage.tsx` 按路径分发。

| 页面 | 路由 | 内容 |
| --- | --- | --- |
| 概念列表 | `#/knowledge/concepts` | 名称、区分标签、主体 / 提及条数、状态；搜索（`SearchBox`）；筛选关注 / 不关注 / 已归档；新建概念 |
| 概念页 | `#/knowledge/concepts?concept=<id>` | 名称、区分标签、别名、关注开关；其下知识点按类型分组（定义、性质、方法、用法…），每条带角色标记；别名用于检索；不显示隐藏的源概念或撤销合并入口 |

操作：

- **挂入知识点：** 弹窗里搜索已有知识点，多选，选角色。
- **知识点行：** 改角色、移出、移到其他概念；点击打开现有知识点详情。
- **概念：** 编辑、合并到…、归档、删除（提示条内可撤销，做法同待办）。
- **知识点详情（`KnowledgeDetail.tsx`）：** 新增“所属概念”一行，显示概念并可添加、移除；类型为 `concept` 的旧知识点显示“由此创建概念”，执行 `createConcept`（名称取标题，该知识点作为主体挂入，用户可在弹窗里改名和填区分标签）。
- **知识点列表：** 分组方式（`KnowledgeGroup`）增加“按概念”，未挂靠的归入“未归入概念”。

实现约束：

- 数据层仿 `todoStore.ts` 写 `conceptStore.ts`（`useSyncExternalStore`，命令成功后合并返回的变更记录，处理 503 不可用）。
- 分组、计数、合并解析都调用 web-core 的视图函数，与服务端同一实现。
- 只读模式下隐藏写操作，沿用现有 `canWrite` 判断。
- 选中态和新组件不使用左侧竖线强调条。

## 7. 第二期：关系与图

- **手工关系：** 概念页增加“关系”区，选择另一端概念和类型；可选一条已同时挂在两端的知识点作为依据。
- **由条目投影：** 一条知识点以主体挂在概念 A、同时提及概念 B 时，概念页和图上显示一条“待定类型”的虚线；用户选定类型后才生成关系记录，`basisItemId` 指向该知识点。没有选类型的虚线不落库。
- **概念图：** 新增适配函数，把 `GET /api/knowledge/concepts` 的结果和知识点列表转成现有 `ConceptGraphData`，`ConceptGraphView` 默认显示真实数据。掌握状态一律为“未评估”。不关注的概念默认隐藏，可切换。现有“导入实验结果”“增量确认演示”“离线报告审阅”三个实验入口保留，收进“实验”菜单。
- 渲染库选型仍未定（见 10-15 备忘），第二期开始前单独决定；本期不阻塞。

## 8. 第三期：AI 挂靠（只列约束）

- 沿用已验证的原版挂靠提示词，不在其中加入粒度规则。
- 输出改为每条知识点给出主体概念和提及概念；接入前先用 10 篇真实笔记验证这种输出是否稳定。
- AI 产出一律 `sourceMode = ai`、`reviewStatus = candidate`，经由服务端内部入口写入；公开命令接口拒绝客户端自称 `ai`（`CONCEPT_AI_SOURCE_RESERVED`）。
- 审阅按风险分级（新建概念、合并、无出处补充、存疑条目必须确认；其余懒确认），界面沿用增量确认演示和离线报告审阅的交互。
- 整理建议（降级、合并、改名、拆分）只展示，采纳后转成第 4 节的命令执行。

## 9. 实施选择

以下选择沿用本方案，并以文首 2026-11-12 用户决定修正合并及连带删除行为：

1. **同步在第一期就做**，云端与 Mac 应用需要一起升级（第 2、5 节）。
2. **关系类型为冻结稿六类加 `isA`**（第 3.3 节）。实验里用的是不含 `causes` 的六类；这里保留 `causes` 以免和冻结稿冲突。
3. **PostgreSQL 用 JSONB 表**，不建外键（第 3.5 节）。
4. **旧的 `knowledgeType = concept` 知识点不自动迁移**，只提供“由此创建概念”（第 6 节）。
5. **知识点永久删除时自动软删除它的关联和关系**，而不是要求用户先手动解除（第 3.4 节）。
6. **冻结稿需要同步修订：** 第 3 章新增 Concept 三类对象；第 3.8 节 `KnowledgeRelation`（连接知识点、自带 `description`）由概念关系取代。建议随第一期 PR 一起改。

| C | PostgreSQL 表、迁移、存储、JSON→PG 迁移、快照备份与恢复 | 真实 PG 测试；备份恢复往返 |

## 11. 风险

- **永久删除联动涉及三条实现路径**（第 5 节末），是本方案里我核对得最少的部分，也是最容易漏的地方。
- **必需能力升级**会让旧版 Mac 应用在升级前无法同步；发布时需要两端同时上线。
- **JSONB 无外键**：引用完整性完全依赖事务内校验，批次 B、C、D 的校验必须是同一套 web-core 函数，不能各写一份。
- **“主体 / 提及”和“条目投影关系”没有实验支持**。第一、二期是手工操作，风险小；第三期接 AI 前必须先验证。
