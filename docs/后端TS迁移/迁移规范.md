# 后端 TS 迁移规范

本文规定 `apps/api` 从 JS 迁到 TS 时每一批**怎么做、做到什么程度、写多少文档**。AI 和审查者都按本文执行；进度与剩余范围见 [迁移计划](迁移计划.md)。

制定原因：第 1–60 批迁了 96 个文件（约 1 万行 TS），但另外新增了约 3.8 万行专项等价测试、8 千行类型测试和 210KB 进度文档，配套投入是迁移代码的 4 倍以上；按这个节奏，剩余 233 个文件（约 3.1 万行）推进不动。本规范自第 61 批起生效。

## 1. 每批的范围

- 一批迁移**一个目录**，或 **5–15 个相互依赖的文件**。不再一批只迁一个文件。
- 除改名外，每批手写 diff 控制在约 **800 行**以内；超出就拆成两批。
- 一批只做类型迁移。发现真 bug 时单独提交（同一 PR 内可以），提交说明写清楚原行为和修正后的行为。

## 2. 怎么迁

1. 用 `git mv x.js x.ts` 改名，保留 `git blame` 历史，不要新建文件再复制内容。
2. 把仓库内所有导入 `./x.js` 的地方改为 `./x.ts`。JS 文件也可以直接导入 `.ts`（Node 24 类型剥离），**不再新建"同名 JS 转发文件"**。
3. 以下文件被外部按 `.js` 路径启动或打包，迁移时**必须在同一 PR 里同步修改引用**，否则保留 `.js` 外壳：

   | 文件 | 引用位置 |
   | --- | --- |
   | `src/main.ts` | `apps/api/package.json`、`deploy/ecosystem.config.cjs`、`scripts/start-dev.mjs` |
   | `src/server.ts` | `apps/desktop-runtime/src/runtime-services.mjs`、`deploy/isolated-test/runtime.mjs` |
   | `src/modules/ai/worker-child.js`、`provider-child.js` | `isolated-worker.js` / `isolated-provider.js` 按路径启动子进程；`apps/desktop-shell/scripts/build.mjs` 按名称打包 |

4. 已有的 96 个转发文件：迁到哪个目录，就在那一批里删掉这个目录的转发文件，并把导入改指 `.ts`。

## 3. 类型写法

- 禁止 `any`、`@ts-ignore`、`@ts-expect-error`、`@ts-nocheck`；只用可擦除语法（`erasableSyntaxOnly` 会检查）。
- **`unknown` 只用于外部输入**：HTTP 请求体、`JSON.parse` 结果、模型输出、数据库原始行、第三方回调参数。模块内部和模块之间的接口用具体类型，不要因为"原 JS 没限制"就把字段写成 `unknown`。
- 错误统一用 `src/errors/app-error.ts` 的 `AppError` / `createAppError`，不再手写 `Error & { code?: string }`。
- 依赖注入的参数（`createXxxService({ ... })`）定义成具名 `interface`，只列出该模块真正用到的方法。
- 类型只描述现有行为，不顺手重构逻辑或改名。

## 4. 测试：只用现有测试验收

迁移期使用下面两条类型检查命令；第 138 批起配置已合并，`typecheck:migrated` 保留为 strict 检查的兼容别名，不再维护另一份配置。后续改动至少运行全量 strict、API 测试与改动文件风格检查，独立审查通过后才可合并：

```bash
npm run typecheck:migrated -w @study-accelerator/api
```

```bash
npm run typecheck:api
```

```bash
npm run test:api
```

```bash
node scripts/lint/run.mjs eslint <本批文件...>
```

（Prettier 同样只对本批文件运行 `--write`。）

**不再新增**以下内容：

- 证明"新代码与旧代码行为一致"的专项测试（`typescript-*.node.test.js` 一类）；
- 冻结旧源码的副本（`*.parent-source.js`）、SHA256 / AST 比对、"变异"测试、`KNOWRA_*_BASELINE` 一类环境开关；
- 每批一个的 `*.type-test.ts`。只有导出给 `packages/web-core` 或前端共用的契约类型，才可以写类型测试，每个不超过 50 行。

如果本批某个文件**完全没有被现有测试执行到**，补的是普通行为测试：放进对应模块的常规测试文件，测业务行为，不测"与旧版一致"。

`test:api` 不再为每批追加文件名；新的 node:test 文件用通配符纳入。

## 5. 文档：每批一行

- [迁移计划](迁移计划.md) 的进度表**每批只加一行**：日期、范围、PR、strict 错误数、宽松错误数、剩余纯 JS 文件数。
- 细节（为什么这样设计类型、发现了什么 bug）写在 **PR 描述**里，不超过 20 行。
- 不在任何文档里记录提交哈希、tree、文件字节数、SHA256、AST 比对结果。
- [工程变更日志](../工程变更日志.md) 每批最多一条，一两句话。

## 6. 存量一次性测试的处理

第 1–60 批留下的专项测试在迁移验证完成后已经没有持续价值，用**一个单独的清理 PR** 处理，不和迁移批次混在一起：

1. 收集覆盖率，找出 40 个没有被常规测试直接导入的已迁模块里，哪些在 `npm run test:api` 中完全没有被执行（可以用 `NODE_V8_COVERAGE=<目录> npm run test:api` 收集，一次性查看，不新增依赖）。
2. 对完全没被执行到的模块，从原专项测试里挑出描述业务行为的用例，改写进常规测试文件，每个模块不超过 100 行。
3. 删除全部 `apps/api/test/typescript-*.node.test.js`、`*.parent-source.js`，以及非共享契约的 `*.type-test.ts`。
4. 把 `package.json` 里 `test:api` 逐个列出的文件名改成通配符。
5. 清理 PR 的验收与普通批次相同，PR 描述里列出删除的文件数、行数，以及补写行为测试的模块。

## 7. 一个目录算"完成"的标准

- 目录内没有纯 JS 文件，也没有转发文件（第 2 节表格中的入口除外）；
- 目录下所有文件都在 `typecheck:migrated`（strict）范围内且 0 错误；
- 进度表里记录该目录完成。

第 138 批完成配置收口：`tsconfig.json` 是唯一 strict 配置，包含全部 `src/**/*.ts` 和既有共享契约类型测试，不再设置 `allowJs` / `checkJs`；`typecheck:api` 为 CI 硬门禁，`Code style report` 仅保留 ESLint / Prettier。新增源码不得通过收窄 include 或恢复 JS 转发入口绕过检查。此处完成的是源码与检查配置，正式 Node 24 CI、发布及部署验收仍以相应运行结果为准。
