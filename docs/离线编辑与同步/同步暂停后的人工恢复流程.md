# 同步暂停后的人工恢复流程

本流程对应保守同步保护，不包含 SQLite v8 格式升级。它优先保存本地意图，当前版本没有自动解除结果待确认暂停的入口。

## 触发条件

- 实体提交已经开始，但网络中断、超时、响应无法识别或本地确认落库失败，无法证明提交结果。
- 服务端返回 `OPERATION_REUSED`、`SYNC_OPERATION_EXPIRED` 或 `DATASET_CHANGED`，不能安全判定原请求从未执行。
- 发现旧版遗留的 v1 请求，或无法证明尚未开始发送的冻结批次。
- 迟到确认不匹配当前操作、原请求或当前已知 epoch。

## 用户看到什么

状态显示“云端同步已暂停”，提示提交结果待人工核对、本地修改已保留。该状态记录在 SQLite 元数据中；重启、立即同步、重新登录、网络恢复或普通冲突处理都不会自动解除。

## 用户可执行的操作

1. 继续在本机保存和编辑资料。
2. 在“云端同步”面板打开“本机备份与恢复”，先创建本机备份并保留原资料目录。
3. 点击“导出冲突恢复记录”，把恢复 JSON 保存在本机受保护的位置。
4. 如果需要核对云端，使用独立的资料目录或只读界面；不要让旧版应用打开这份资料库，也不要改设备编号、操作 ID 或数据库元数据来强制同步。

## 每个操作的后果

- 继续编辑只增加本地修改，不提交这份资料库的待确认请求。
- 本机备份保存数据库和备份机制覆盖的附件；原目录及备份都应保留，导出 JSON 不能替代附件备份。
- 恢复 JSON 包含当前实体、冻结批次、legacy 原请求、outbox 和暂停原因，可能含私人笔记，应按私人资料保管。
- “立即同步”保持暂停；重新配置和普通冲突处理会被保护拒绝。恢复该资料库的备份也保留暂停状态，不会成为绕过保护的入口。
- 此版本保持 SQLite v7；旧版应用不理解这些保护标记，因此不要通过降级应用尝试恢复同步。

## 数据不丢失的依据

- 网络提交前先持久记录发送状态；崩溃后发现未确认发送也会停止。
- 结果未知时保留原请求、本地实体、后续编辑、outbox 和同步基线，不因回执 missing、epoch 改变或普通重试而清理或替换它们。
- 迟到结果先检查当前请求和 epoch，检查失败不更新基线、删除事实或后续队列。
- 暂停后仍可导出当前本地状态和原始请求；完整 SQLite 备份另行保留数据库恢复证据。

## 缺口

- 没有“核对回执后安全恢复”“撤销在途请求”或“服务端屏障后换 ID”的产品入口，不能承诺点击某个按钮即可恢复同步。
- 需要人工同时保全本地当前状态和云端当前状态，再确定修复方案。当前代码不执行这一步，也不自动重新提交。
- 本次没有采用 SQLite v8 门禁，不能阻止不理解保护标记的旧版应用读取同一 v7 资料库；是否采用不可逆门禁仍需用户单独决定。
- 真实 Mac 降级、物理断电及历史版本兼容演练不在本轮验证范围。
