# SQLite v8 兼容门禁与回退边界

## 范围与用户取舍

v8 是本机 SQLite 的强制兼容门禁，不是业务快照 schema8，也不是 AI 的第八版。用户已接受：升级后，不支持 v8 的旧应用不能再直接打开该库；回退需要升级前备份与安全恢复流程。当前只用临时合成资料验证，没有升级真实资料库、安装、部署或进行真实旧版/断电演练。

门禁与保守同步保护必须一起发布。单独把版本改成 8，不能证明同步恢复已经安全。运行时启动失败会沿用已有错误提示；旧 v7 初始化器遇到 v8 提示“本地数据库版本 8 不支持，请升级应用”，并停止初始化。

## 初始化与迁移顺序

- `PRAGMA user_version = 8` 表示必须使用支持 v8 的应用。AI 私有表的进度独立存为 `metadata.aiSchemaVersion`，范围为 3–7。
- 已有 v3–v7 库在门禁事务之前用 `VACUUM INTO` 创建唯一命名的 `local.sqlite.before-v8-*.bak`，校验副本版本与 `integrity_check`、设为 0600 并同步文件。POSIX 另同步所在目录；Windows 不对目录执行 fsync。
- 备份失败即停止。门禁事务只新增 AI 进度并设置 user_version；它不更换任何设备/资料集身份、不重写冻结请求/队列/已发送事实，也不清除同步暂停或恢复会话。
- 门禁事务失败时，v3–v7 原版本及记录回滚，已校验副本保留。v7 合成用例同时验证原库和副本仍通过冻结的旧 v7 初始化入口。
- 门禁成功后，可选 AI 按独立进度分段迁移。AI 失败只关闭 AI，user_version 仍是 8；不能降回 v7 来“恢复可用”，否则旧版会绕过保护。重启只按保留的进度重试。v8 的 AI 描述符缺失或未知时停止启动，不猜测覆盖。
- 新空库先创建核心表，再写入 v8 门禁，然后尝试 AI 初始化；不会给已有未标版本表或截断文件初始化空库。

## 不得扩大解释的边界

1. v1/v2 沿用既有的 v1→v2→v3 分段事务和各阶段备份，再进入 v8。它们不是从起点到 v8 的单一原子迁移。若在 v8 门禁阶段失败，当前库可以已经是 v3；合成测试验证这一事实及原 v1/v2 备份仍在，而非声称失败自动回到 v1。
2. `.before-v8-*.bak` 只是一份 SQLite 数据库快照，包含库内业务、队列和私有记录，不含 `uploads/` 附件文件、根目录草稿及其他文件。它不是“完整 App 备份”，也没有完整备份清单。附件仍需独立保全并与对应数据库核对。
3. 备份和事务测试覆盖正常文件系统上的明确失败与回滚，不构成真实断电、硬盘损坏、跨文件持久化或未知历史二进制的承诺。没有修改正在使用的真实库来验证回退。
4. 门禁不能禁止人为修改 PRAGMA，也不保护缺少未知版本拒绝逻辑的任意古老/第三方客户端。已验证的是基线 `654714d2` 的冻结 v7 初始化代码拒绝 v8，不是所有旧安装包的逐一实机认证；产品版本号相同也可能来自不同构建。
5. 只读救援与完整备份检查不迁移来源，仍走私有临时 SQLite 快照。v8 的 AI 校验必须读独立进度，不能把 user_version8 误当成 AI 表都已完成。

## 回退到旧版的安全原则

- 不在原目录降级，不手工把 user_version 改回 7，不用旧应用试开 v8 来碰运气。
- 先停止所有知境实例，保留完整当前资料目录及匹配的附件/草稿；不要删除 v8 库、WAL/SHM 或升级前副本。使用只读救援路径检查原始资料。
- 在新的隔离目录中准备升级前数据库及与它匹配的附件/其他文件，再用明确兼容的旧构建核验。新产生的 v8 本机改动不能靠覆盖旧库自动保留。
- 如果该设备曾连接同步、已有待确认/暂停/退役/恢复会话或新旧发送身份，回退库也可能携带旧请求。不能直接联网重放；必须先按服务端退役屏障和新身份的安全流程核对。备份可读取不等于旧身份可以重新同步。
- 官方完整恢复仍生成新资料集并保持同步暂停；原活动目录保留。此流程用于受支持格式的恢复，不是把 v8 数据降为 v7。

## #340 组合与旧未完成会话

此候选以 #340 的 `dc7b83b4` 为同步语义基线。新创建的恢复会话记录 `backupHashVersion: 2`；新 hash 同时覆盖 `user_version`、用户定义表/索引/触发器的 SQL 结构及完整用户表记录。已重签文件清单、单独检查仍然有效但版本或结构不同的副本，也不能替代当前恢复所需的同格式完整备份。

已有未版本化的未完成会话不会被静默补写 hash、清除或换号。升级后的“继续恢复”和“最终选择”都会在联网退役/切换前返回 `SYNC_RECOVERY_UPGRADE_REQUIRED`，原会话（包括 ID、新发送编号、hash、下载与屏障证明）、冻结请求、暂停和队列均保留。合成回归覆盖 v7 `retiring` 与 `preview` 两阶段升级到 v8 的保守停止。已完成会话不因缺少新字段而重新打开。

**这是明确的旧会话恢复缺口，不是所有历史会话已经闭环。** 当前没有提供“点一下继续”的旧会话安全迁移功能，也不能通过复制新的资料集来复用旧恢复编号。正常新建 v8 会话和官方完整恢复的另一资料集保护分别走已有回归。

### 当前可执行路径

- 当前仅合成候选，用户真实资料尚未升级，不需要在真实库上做任何降级或修复。
- 将来若准备采用 v8，先在现有受支持应用中查看是否还有同步暂停/未完成恢复。只要仍有，先保留完整资料目录并用正式完整备份/只读救援导出核验附件与草稿；不要为了升级删掉暂停或会话。
- 升级后若看到旧会话提示，可以继续保留本机编辑并导出救援副本，但不要反复退役、直接联网重放、手工改版本或用旧安装包打开原目录。保留源目录、原升级前副本及服务端当前作废账本，等待受审的专用迁移方案。
- 若要从升级前备份取回正文，只能在隔离的新目录中只读核对并对照导出，不把该备份的旧同步身份接回线上。人工取回内容也不等于恢复会话已经安全结束。

### 后续安全迁移的可行方案（仅设计，未实施）

可以保留原 `backupHash` 及所有身份/证明，再额外建立 v2 备份证据，而不篡改旧 hash 来迎合新算法。实施前必须：只读校验原 v7 完整备份及原逐表 hash；核对原请求/暂停事实、所属服务与资料集；查询同一退役命令和固定新编号的服务端状态；对尚未退役、确认丢失、已退役、快照下载中/预览等状态分别分支。存在屏障时必须保持同一恢复 ID/新编号，确认新编号尚未被使用，且不额外发送退役请求。

再为当前 v8 完整资料创建并核验新格式备份，原子追加独立证据而不清除旧证据；重新核对固定快照/预览修订，最终提交前仍做第二次当前完整备份。必须补齐原备份损坏、版本/结构不明、服务端账本丢失、外部修改、不同 dataset、新编号已用、重启与提交失败等负向回归后再独立审查。当前不承诺此设计已经可用或一定能迁移每个旧现场。

## 合成验证入口

- `node --test apps/desktop-runtime/test/sqlite-v8-gate.test.mjs`：v1–v7 形状、v7 升级前副本、冻结旧入口拒开、备份权限/同步失败、门禁回滚、AI 失败与重试、未知描述符、完整备份及官方恢复。
- `npm run test:desktop`：现有本地存储、AI、备份、同步与恢复回归。真实 PostgreSQL 用例未配置时会跳过，不能据此声称真实 PG 通过。
- `npm run test:scripts`：既有只读资料核对和救援契约。

组合定向还覆盖同记录不同版本/索引的备份拒绝、旧未版本化会话升级暂停、已有另一 dataset 不能复用会话以及完整新 v8 恢复流程。

CI 的 desktop suite 通过 `test/*.test.mjs` 自动纳入新增门禁测试；此文不替代精确提交的实际 CI 与独立审查结果。实际执行结果与精确提交 CI 在 PR 记录；未通过的完整门禁不能被定向通过替代。
