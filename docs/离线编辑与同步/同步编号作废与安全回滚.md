# 同步编号作废与安全回滚

本页描述服务端屏障基础层。客户端仍保留结果待确认暂停；当前没有据此自动换号、重传或解锁冲突的入口。本功能不包含 SQLite v8 升级、安装、部署或真实资料维护。

## 何时生效

- 查询状态、原操作回执和恢复记录都是只读，不作废编号、不升级格式。
- 只有明确发起 `POST /api/sync/device-retirement`，带 `action: retire-device` 和 `acceptJournalUpgrade: true`，才会尝试建立屏障。
- 请求绑定服务端所属资料库、当前 epoch、旧编号、新编号、固定恢复编号和原请求身份。请求不包含正文。
- 旧、新编号都必须符合现有设备准入规则；不在白名单中的新编号会使整个动作失败，不会先作废旧编号，也不会修改白名单。

## 屏障及兼容后果

- 作废事实与服务端 journal 版本 2 在同一写事务提交；此后旧编号不能再进行 v1 或 v2 业务写入，序号更大或换操作 ID 也不能继续。
- 旧请求先提交时，其结果保留；屏障先提交时，迟到旧请求在真正业务事务中被拒绝。请求入站时检查不能替代事务内检查。
- 精确匹配的已保存回执可只读返回，不会重放业务写入；回执淘汰后仍按作废事实拒绝写入。
- JSON 使用同一原子替换事务；PG 使用既有同一 advisory transaction lock。PG 内不做外部文件或网络 IO。
- 已开始的附件字节传输可能完成，但不能绕过后续实体批次事务的屏障。屏障不撤销已经提交的业务，也不承诺取消已经发送的网络包。
- 不理解 journal 版本 2 的旧服务端会拒绝读取。正常运行、预检或新版本启动不会提前升级版本；首次明确作废动作才建立门禁。
- 这不是用户认证机制，不能防止有原有写入权限的人伪造其他全新设备编号；它用于拒绝已作废的旧同步身份及其迟到请求。

## 结果未知时

- 发起前必须在本地持久保存恢复编号、新编号、原请求身份及本地完整恢复证据；此客户端流程尚待实现，不能手改数据库代替。
- 响应丢失时查询 `GET /api/sync/device-retirement`，使用同一旧编号和恢复编号。不能换恢复编号或新编号重复发起。
- 相同绑定重复请求返回同一证明；任何原请求、新编号或恢复编号的替换都被拒绝。
- 取得屏障证明不等于可以清空本地请求。还须保全本地当前状态、原基线及后继编辑，取得权威快照，按关联组显式处理冲突。
- 缺回执、conflict 或 epoch 变更不能通过普通确认或普通拉取解锁；尤其不能丢失“原 false → 提交 true → 本地 false”的撤回意图。

## 支持的内容回滚

1. 保留当前已受保护的服务端资料库及其最新作废记录，不覆盖其物理文件或 journal 行。
2. 将旧业务内容通过现有 JSON `commitImport`，或现有 PostgreSQL 业务导入流程恢复到该目标；它们保留目标作废事实及版本 2，并生成新 epoch。
3. 同步世代维护重建也保留作废事实和版本 2。PG 导入若会删除其他所属资料库的受保护记录，则整体拒绝。
4. 使用支持版本 2 的服务端核对。旧编号仍被拒绝，新编号仍遵守当前白名单；不得为了恢复修改准入权限。

直接把物理 JSON/PG 数据和 journal 一起替换成屏障前的裸备份，会把作废事实一起回滚。单个 journal 不能证明自身曾被回滚；该操作不属于安全恢复流程，不能声称安全。当前目标或最新作废账本不可用时必须停下人工处理，不初始化空账本后继续同步。

## 验证范围与缺口

- 合成测试覆盖显式动作、格式接受、写入失败回滚、重启、v1/v2、迟到事务、回执淘汰、幂等绑定、白名单及受支持内容回滚。
- 使用升级前主线的原始 `loadJournal` 源码验证旧读取器拒绝版本 2；不等于真实旧安装包兼容演练。
- 真实 PG、旧安装包、物理断电及裸备份运维演练未因此得到验证。
- 客户端临时认证、完整恢复预检、新同步身份持久化及关联冲突处理尚未接入，当前不能宣称端到端恢复闭环。
