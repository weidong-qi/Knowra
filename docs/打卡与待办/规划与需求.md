# 打卡与待办：规划与需求

更新日期：2026-10-31  
文档状态：待办核心需求已讨论确认；打卡、经验等级与时代仍待后续细化，尚未进入实现。

本目录作为「打卡与待办」模块的工作区，用于沉淀需求讨论、交互方案、实施计划与验收记录。本文以本轮讨论最终确认的规则为准；未决事项另行列出，不将早期建议或竞品行为当作已经确认的需求。

## 一、模块定位与首版边界

希望在知境中建立一个既能承接长期目标，也能随手记录日常小事的地方。

- **主线**：有明确终点、能够判断是否达成的目标，支持长期规划与灵活拆解。
- **支线**：琐碎事项或临时想到的小事，可以带有步骤，也可以随着事情发展转入主线体系。
- **打卡**：记录持续行动的方向已提出，具体规则尚待讨论。
- **时代（Era）**：承载宏观人生方向、阶段主题、态度、目标和生活记录的远期愿景，暂不开发。

当前先把待办独立做好。首版纳入主线／支线、任务拆解与转换、今日安排、日期规划、星标、暂停、完成、主动通知、删除和归档。

首版暂不做笔记关联、从笔记创建任务、笔记中的相关任务入口，也不做日历式计划视图。经验与等级系统、时代功能留待后续；打卡的首版范围另行讨论，不能直接套用待办规则。

本文是需求记录，不代表功能已经实现，也未确定技术方案或开发排期。

## 二、主线与支线

### 1. 主线：有终点，允许边做边调整

主线围绕一个可结束、可回顾的目标展开。例如「完成一个图像分类项目」适合作为主线；「探索技术方向」等宏观主题可以交给时代承载。

- 一个主线可以包含多个任务，任务可以继续嵌套子任务。
- 不固定为「阶段 → 任务 → 子任务」的结构；可以用较大的任务组织阶段，也可以直接列具体行动。
- 允许先记录目标，再边做边添加、修改、拆解和调整顺序、层级及归属，不要求提前写完整计划。
- 明确终点不意味着必须填写截止日期。
- 任务完成数量用于展示进展，不直接等同于整个目标的完成百分比。

以下仅为结构示例，不是用户已经建立的实际任务：

```text
主线：完成图像分类项目
├── 准备数据
├── 训练模型
│   ├── 编写训练循环
│   └── 运行首次训练
└── 整理结果
```

### 2. 支线：轻量记录，也能拆成步骤

支线承接临时想到、需要先记下来的事项，不要求它们具有长期目标或完整规划。

- 支线可以包含步骤，如「办理报销」下列出整理票据、填写申请、提交材料。
- 有步骤不意味着必须升级为主线；两者的区别在于目标与规划的规模。
- 支线不代表一定不重要或不紧急，重要程度与日期分别表达。
- 主线中的子任务不因规模小而自动被称为支线；它仍属于该目标的拆解。

### 3. 支线转换与移动

| 操作 | 结果 |
| --- | --- |
| 支线升级为主线 | 形成独立主线，保留名称、说明、步骤与完成记录，可以再补充目标说明 |
| 支线移入已有主线 | 选择主线及放置位置，连同步骤整体成为其中的子任务 |
| 转换或移动后 | 保留一份任务及其进展，不在原支线列表中复制保留另一份 |

归档后的任务不再允许转换或移动，归档边界见第九节。

## 三、任务信息与重要程度

创建保持轻量，名称作为必填信息；任务自身保留简短说明，其他信息按需补充。

| 信息 | 用途 |
| --- | --- |
| 名称 | 用一句话记录要做的事情 |
| 说明 | 可选，补充背景、要求或想法 |
| 目标说明与完成标准 | 主线可逐步补充，用于判断目标是否达成，不强制创建时填写完整 |
| 子任务／步骤 | 按需拆解，随进展调整 |
| 计划日期 | 准备哪一天做，可选 |
| 截止日期 | 最晚必须完成的日期，可选 |
| 星标 | 只有星标／无星标，不设置高、中、低多档优先级 |
| 提醒 | 主动设置的通知，见第八节 |

主线、支线及具体子任务可以独立标星。星标表达关注程度，不代替日期或逾期判断。首版不接入笔记关联。

## 四、任务状态与暂停规则

### 1. 三个日常状态

| 状态 | 含义 |
| --- | --- |
| 进行中 | 包含尚未开始与正在推进，新建默认使用此状态 |
| 已暂停 | 主动搁置或暂时无法推进，之后可能继续 |
| 已完成 | 已经做成，尚未归档时仍可以整理或重新打开 |

不单设「待开始」「阻塞」「不再做」状态。不再需要且未归档的任务通过删除处理。

「已归档」是完成之后的最终封存状态，区别于以上三个日常状态；不提供从归档返回日常状态的操作。

```text
进行中 ⇄ 已暂停
   ↓
已完成 → 已归档
```

该图表示主要流程；已完成但未归档的任务可以重新打开，回到进行中。

### 2. 暂停与恢复

- 暂停原因可选填，如「等数据」「这段时间先忙其他事」。
- 暂停期间仍允许编辑说明、调整任务结构和子任务。
- 暂停整条主线或父任务时，未完成下级一起暂停参与日常安排，从「今日安排」「之前未完成」中收起；已完成记录保留。
- 单独暂停某个子任务，不影响其他任务推进。
- 恢复父任务时，随父任务暂停的下级恢复；此前单独暂停的下级继续保持暂停。
- 保留计划日期与截止日期，不自动顺延。暂停不会取消逾期事实，超过截止日期仍需显示逾期信息。
- 恢复时若计划日期已过，任务进入「之前未完成」，供用户重新安排。
- 暂停期间的主动通知停止，恢复规则见第八节。

## 五、日期、今日安排与逾期

### 1. 两种日期，分别表达

| 日期 | 含义 | 错过后的处理 |
| --- | --- | --- |
| 计划日期 | 准备哪一天做 | 未完成则进入「之前未完成」，不因此称为逾期 |
| 截止日期 | 最晚什么时候必须完成 | 超过截止日期仍未完成，标记「逾期」 |

例如材料周五截止，可以安排周三处理。周三没做完需要重新安排，但还没有超过截止期限。

### 2. 各任务独立安排

- 父任务、子任务和步骤各自安排日期，不因父任务设置日期而自动继承。
- 父任务安排在今天，不会把全部下级自动安排到今天；可以展开查看下级，但下级只有自己符合日期或手动选入条件时，才独立进入今日安排。
- 父任务改期，不自动修改下级日期。
- 主线截止日期约束整体目标，但不自动复制给每个下级。
- 子任务安排晚于主线截止日期等冲突需要提示，允许用户保留或调整，不强制阻止。

### 3. 两种进入今天的方式

- **手动选入**：把准备今天做的事项加入今天。
- **提前安排**：设定计划日期，到当天自动进入今日安排。
- 主线中的具体任务、支线及其步骤均可参与今日安排。
- 进入今天只是视图与日期安排的变化，保留原有归属；在今天完成后，原位置同步更新。
- 同一事项只显示一份，不因同时符合手动与日期条件而重复。

采用一套计划日期规则：「加入今天」将计划日期设为今天；已有未来计划日期时，操作明确显示为「改到今天」，告知会改变原安排。

### 4. 跨天未完成

「今天」包含今日安排、之前未完成、今日已完成，并突出截止与逾期信息。

- 跨天未完成的已安排事项进入「之前未完成」，保留原计划日期，不自动改到次日。
- 可以直接完成，或选择「今天继续」「改期」「取消日期安排」。
- 取消计划日期后，任务仍保留在原主线或支线中，不等于删除；截止日期独立保留。
- 「之前未完成」支持折叠并保留数量，支持批量安排，减少逐项整理。
- 仅错过计划日期使用中性提示；只有超过截止日期才标记逾期。
- 今日截止或已逾期事项需要明显提示，不随普通积压事项折叠后失去可见提示。具体布局后续设计。
- 暂停事项不混入日常行动列表，但暂停列表或相关详情仍应保留其截止、逾期信息。

## 六、完成、重新打开与删除

### 1. 手动完成父任务，提供快捷收尾

- 无下级的任务或步骤可以直接勾选完成。
- 最后一个下级完成后，不自动完成父任务，也不弹确认框；就地提示「所有步骤已完成」，提供完成父任务的快捷按钮。
- 父任务没有未完成下级时，勾选即可完成，不重复二次确认。
- 父任务还有未完成下级时，不能静默连带完成；先提示用户选择「全部标为完成」或返回整理。
- 不需要的下级先删除，再完成父任务。不再提供早期讨论中的「剩余标为不再做」选项。
- 主线始终由用户主动确认完成，子任务全部完成不代表目标一定达成。
- 完成操作支持撤销；未归档的已完成任务可以重新打开，保留此前的完成记录。

任务拆解代表当前计划，完成现有步骤后仍可发现新工作。因此，在未归档阶段保留调整与重新打开的空间。

### 2. 删除

- 不再需要的未归档任务可以直接删除，不增加「不再做」状态。
- 删除支持撤销。
- 删除带下级的任务或整条主线时，明确提示会连同下级一起删除。
- 已归档任务不能删除，也不能借助删除其父级等方式绕过封存边界。
- 删除撤销的有效范围、回收站与恢复保留周期尚未确定，不预设永久历史保留机制。

## 七、页面入口与下一步行动

### 1. 四个入口

| 入口 | 主要内容 |
| --- | --- |
| 今天 | 今日安排、之前未完成、今日已完成，突出截止与逾期信息 |
| 主线 | 长期目标列表，进入后查看并调整任务树 |
| 支线 | 零散待办，可展开查看步骤 |
| 计划 | 按日期分组查看未来安排并改期，首版不做日历或按小时拖拽排程 |

- 「已暂停」「已完成」作为主线、支线的筛选项，不新增独立主导航；新增的「已归档」也通过筛选查看。
- 星标作为筛选条件，保留手动排序。
- 通用快速添加默认建立支线，只填名称即可保存；在主线内部添加，默认成为该主线的子任务。
- 主线列表优先展示名称、星标、任务进展、下一步行动及可选截止日期。完整树结构在进入主线后查看。

### 2. 下一步由任务排序决定

不额外维护「手动指定下一步」字段，按用户排列的任务顺序自动确定：

1. 从上往下寻找第一个未完成、未暂停的任务。
2. 如果该任务还有未完成下级，继续逐层向下寻找具体可执行项。
3. 已完成项跳过；暂停父任务及其整个下级分支均跳过。
4. 某个父任务的下级全部完成、父任务尚未结束时，显示「确认完成：父任务名称」。
5. 调整排序或完成当前项后，下一步随之更新。

「下一步」仅表达推进顺序，不自动加入今天、不修改日期。若排在前面的任务计划在未来，仍可显示为下一步，并同时显示其计划日期，不把排序自动改成日期排序。

例如以下任务树的下一步为「编写训练循环」，完成后显示「运行首次训练」：

```text
完成分类项目
├── 准备数据 ✓
├── 训练模型
│   ├── 编写训练循环
│   └── 运行首次训练
└── 整理结果
```

若下级并非全部完成、只是剩余项全部暂停，不应误提示父任务已经满足收尾条件；此类无可执行项的空状态文案留待交互设计。

## 八、主动通知

首版支持主动通知，与「到日期自动进入今天」分别处理。

| 项目 | 确定规则 |
| --- | --- |
| 提醒对象 | 主线、支线及子任务均可独立设置 |
| 设置方式 | 指定日期时间，或选择「截止前一天」等相对截止时间 |
| 默认行为 | 仅填写计划日期或截止日期不自动开启通知；截止与逾期仍在页面提示 |
| 数量与频率 | 首版每项一个提醒时间，触发一次，不反复催促 |
| 截止日期调整 | 相对截止时间的提醒跟随调整 |
| 固定时间提醒 | 保持原时间，日期调整产生冲突时提示 |
| 完成或删除 | 取消尚未触发的提醒 |
| 暂停 | 停止该任务及随之暂停下级的全部主动通知，包括截止提醒；保留日期与提醒设置 |
| 恢复 | 未来的提醒继续生效；已错过的提醒提示重新设置，不集中补发 |

已归档任务没有待触发提醒。通知权限、应用关闭时的通知能力和各端支持范围，需要在技术方案中明确，本次不承诺尚未验证的平台行为。

## 九、归档：正式完结与记录封存

### 1. 已完成与已归档的区别

- **已完成**：事情已做成，仍可以修改、补充说明或重新打开。
- **已归档**：正式完结，只允许查看，不再对任务进行任何修改。

已完成但未归档的阶段，用于检查记录、补充总结和处理遗漏。归档由用户主动操作，不在完成时自动执行。

### 2. 归档规则

| 场景 | 确定规则 |
| --- | --- |
| 归档资格 | 仅已完成任务可以归档 |
| 下级检查 | 仍有未完成下级时，先处理剩余内容再归档，不能把未结束事项直接锁进去 |
| 归档主线或支线 | 连同全部子任务、步骤及原有结构一起封存 |
| 归档前提示 | 明确此次封存范围，以及归档后无法修改 |
| 记录保留 | 保留原结构、完成时间和归档时间 |
| 查阅入口 | 在「已归档」筛选中查看 |
| 取消归档 | 首版不提供 |

归档后禁止修改名称、说明、日期、星标、层级或归属，禁止添加步骤、转换任务、重新打开、删除等操作。归档主线下的内容不能借由其他入口被修改。

这意味着归档不是普通的「从列表隐藏」，也不是可随时恢复的暂停操作，而是最终封存。若后续支持下级单独归档，父级的移动、删除及结构调整同样不能绕过这一边界；具体冲突处理交互待细化。

## 十、打卡与经验等级：后续规划

### 1. 打卡方向

已明确希望规划打卡功能，但打卡对象、频率、记录内容、统计及补卡规则尚未确认。

以下保留为待讨论方向，不作为首版已确认能力：

| 方向 | 待讨论内容 |
| --- | --- |
| 打卡项目 | 每日、每周、指定日期或自由频率 |
| 记录内容 | 完成标记、文字、次数、时长或图片 |
| 历史回顾 | 记录列表、日历、连续天数或其他统计 |
| 与主线关联 | 是否关联，以及是否影响任务进展 |
| 修正记录 | 补卡、撤销与实际发生日期的处理 |
| 与待办联动 | 打卡是否完成待办、完成待办是否产生打卡 |

### 2. 修仙式经验与等级愿景

用户希望后续建立类似修仙的等级系统，完成打卡可以获得经验。当前仅记录方向，经验数值、等级或境界、升级条件等留待后续细化。

- 任务归档提供不可再修改的完结记录。
- 完成打卡、完成任务和归档任务是不同动作，不预设使用同一套奖励规则。
- 任务是否也奖励经验、奖励在完成还是归档时结算，目前未确定。
- 撤销、删除、补卡及防止重复领取等对经验的影响，在等级系统设计时一并讨论。
- 不将归档默认设计成领取经验的按钮，也不让首版待办依赖等级系统。

## 十一、远期愿景：时代（Era）

### 1. 灵感与定位

「时代」的灵感来自用户对 Taylor Swift 专辑时代的理解：每张专辑代表不同的风格、人生态度、阶段与目标。

在知境中，一个时代可以代表一段很长的人生阶段，承载宏观人生方向与阶段主题。主线则承接其中有明确终点的具体目标；当前无需先建立时代才能使用待办，未来再设计关联方式。

例如，「探索自己的技术方向」可以作为时代主题，「完成一个图像分类项目」可以作为具体主线。此例仅用于说明概念关系。

### 2. 目标与生活共同记录

用户希望时代未来能够容纳：

- 阶段规划与目标：这一阶段想实现什么、朝哪个方向努力。
- 努力过程：围绕目标推进的任务和持续行动，具体关联方式待设计。
- 生活记录：一张照片、看过的一部电影、玩过的一个游戏，以及其他日常片段。
- 日期：为生活片段标上日期，留下每一天生活的痕迹。

生活记录本身有意义，不必都对应工作目标或待办完成结果。时代可以帮助未来的自己回看：那时在追求什么，又是怎样度过那段时间的。

时代目前保留为远期愿景，暂不实现时代管理、生活时间线或媒体记录功能。持续时间是否预先确定、是否允许多个时代并存、何时结束或进入下一个时代，以及展示方式，都留待后续讨论。

## 十二、仍需细化的事项与实施边界

以下问题尚未确定，不阻碍本轮核心需求结论，也不应在实现时默认为已获确认：

1. **嵌套与步骤细节**：最大层级、支线步骤是否允许继续嵌套，以及具体移动交互。
2. **进展与展示**：任务数量按直接下级还是全部下级统计，暂停项如何计数，下一步无可执行项时的呈现。
3. **状态联动边界**：重新打开已完成子任务时，未归档父级是否自动恢复，以及撤销批量完成的具体范围。
4. **删除恢复**：撤销有效期、是否设置回收站及保留周期；归档记录不允许删除的规则不因此改变。
5. **局部归档**：下级单独归档后的父级结构调整与封存冲突如何提示和处理。
6. **日期与通知细节**：是否支持截止具体时刻、跨时区规则、通知权限与应用关闭时的投递能力；不得把「停止重复催促」误做成丢失已设置的未来提醒。
7. **完整交互**：快速添加、任务详情、拖拽排序、空状态、筛选、批量操作和归档前确认的页面设计。
8. **未来模块**：打卡、经验等级、笔记关联与时代的详细规则、范围和推进顺序。
