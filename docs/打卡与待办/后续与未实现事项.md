# 打卡与待办：后续与未实现事项

更新日期：2026-11-09
依据：[规划与需求](规划与需求.md)、[个人待办首版-技术方案](个人待办首版-技术方案.md)，以及首版实现（PR #357）。

本文汇总首版**没有做**的内容，分三类：需求已提出但未进入开发的模块、首版有意简化的能力、尚未验证或需要补的工程项。每项标出是否还需要先做产品决定。

---

## 一、尚未开发的模块（需先讨论规则）

| 模块 | 现状 | 开发前需要确定 |
| --- | --- | --- |
| 打卡 | 只有方向，规则未讨论 | 打卡对象与频率（每日／每周／指定日期／自由）、记录内容（勾选／文字／次数／时长／图片）、历史回顾形式、补卡与撤销、与主线和待办是否联动 |
| 经验与等级（修仙式境界） | 只有愿景 | 经验数值、境界划分与升级条件；打卡、完成任务、归档是否奖励及何时结算；撤销、删除、补卡对经验的影响与防重复领取 |
| 时代（Era） | 远期愿景 | 是否预设时长、能否多个并存、如何结束或切换；与主线的关联方式；生活记录（照片、电影、游戏等）的形态与展示 |
| 笔记关联 | 首版明确不做 | 是否支持从笔记创建任务、在笔记中显示相关任务、任务引用笔记；链接失效与删除时的处理 |

## 二、首版有意简化的能力

### 1. 视图与交互

- **日历视图、按小时排程**：首版「计划」只按日期分组列表，不做月历或时间轴拖拽。
- **拖拽排序**：首版用「上移／下移」菜单调整顺序，拖拽交互未设计。
- **移动的精确位置**：「移动到…」只能移入某条主线的顶层末尾，或移出为独立支线；不能直接移到某个父任务下面或指定位置（需要设计目标选择交互）。
- **多选与批量操作**：只有「之前未完成」分组提供「全部今天继续／全部取消安排」；跨列表多选、批量改期、批量完成未做。
- **待办搜索与快捷键**：待办未接入全局搜索（CmdK），也没有专用键盘快捷键。
- **空状态细化**：主线剩余步骤全部暂停时只显示一句「剩余步骤都已暂停」，需求中提到的交互文案待设计。

### 2. 规则层面的待定项（需求第十二节）

- **层级上限**：首版固定最多 5 层，是否调整待定。
- **进展统计口径**：首版按直接下级统计、暂停项计入总数并单独标出；是否改为统计全部下级待定。
- **重新打开子任务时父级的处理**：首版规则是「已完成的上级一并重新打开」，需求未最终确认。
- **撤销批量完成的范围**：「连同步骤全部完成」后点撤销，首版只重新打开父任务，步骤保持已完成。
- **局部归档**：首版只能整条归档主线或支线；子任务单独归档、以及归档后父级结构调整的冲突处理未设计。
- **截止具体时刻与跨时区**：截止日期只到日期，不支持具体时刻；跨时区出行时「今天」按设备本地日期计算。

### 3. 删除与回收

- **回收站**：首版只有 10 秒内撤销，没有回收站。
- **删除记录的清理**：删除是软删除（记录保留 `deletedAt` 并随同步传播），目前没有任何清理，记录会一直保留。需要确定保留期限和清理方式（清理需同时考虑同步墓碑，不能让已删除记录在其他设备复活）。

### 4. 提醒

- **应用关闭时的提醒**：首版只在应用打开期间投递；关闭期间到期的标为「已错过」、不补发。若要关闭时也能提醒，需要评估 Mac 系统级预约通知或服务端推送，并确认各端权限。
- **网页系统通知**：网页版只在页面内弹提示卡，未申请浏览器通知权限。
- **多次或重复提醒**：首版每项一个提醒、只触发一次。
- **跨设备重复弹出**：两台设备都开着且尚未同步时，同一提醒可能各弹一次（首版已接受）。

### 5. 同步冲突

- 同一条待办在两端都改过时，只能整条「采用本地」或「采用云端」，没有字段级合并。若实际使用中冲突较多，再考虑按字段自动合并（例如一端改标题、另一端改日期）。

## 三、尚未验证或需要补的工程项

| 事项 | 说明 |
| --- | --- |
| Mac 打包后的系统通知 | 代码复用已有通知通道，但未在打包安装的 Mac 应用中实际验证弹出 |
| 云端与 Mac 同步升级的部署 | `personal-todos-v1` 是必需同步能力，云端与 Mac 应用需同时升级；尚未部署，也未在真实云端与 Mac 之间做端到端验收 |
| 端到端测试 | 已有单元、组件、API、双 SQLite 设备同步测试；尚未补 Playwright 页面级 E2E |
| 真实 PostgreSQL 部署 | 已在本机临时 PostgreSQL 上通过测试；生产目前使用 JSON 存储，未在生产 PostgreSQL 上验证 |
| 性能 | 首版每次读取全部待办、在前端组装视图，个人数据量下足够；数据量大后可能需要分页或按需读取 |

## 四、建议的推进顺序

1. **先上线并试用首版**：部署（云端与 Mac 同时升级），在 Mac 真机上确认系统通知，按实际使用反馈调整第二节中的默认规则。
2. **补删除记录的清理策略**：这是唯一会随时间持续累积的问题，建议在试用一段时间后优先处理。
3. **讨论打卡规则**：打卡是需求里明确想做的下一个模块，规则讨论清楚后再进入方案与开发；经验等级在打卡之后设计。
4. **视图增强按需排期**：日历视图、拖拽排序、批量操作、精确移动等根据试用中的痛点决定先后。
5. **时代与笔记关联**保持远期规划。
